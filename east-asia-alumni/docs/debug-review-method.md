# デュアルレビュー デバッグ手法

## 概要

詰まったバグを「2人の独立したレビュワー」として段階的に分析する手法。
同じ問題を長く見ていると思い込みが生まれるため、視点をリセットして再評価する。

Claude Code では `/debug-review` コマンドで呼び出せる。

---

## 手順

### Round 1：1人目のレビュワー（フラットな目）

> 「今日このプロジェクトに初めてアサインされたテスター」として読む

- **コードを全部読む**（既存の議論は一旦忘れる）
- **怪しい点をすべてメモ**（フィルタリングしない）
- **考えられる原因をリストアップ**（「これはないだろう」も含めて全部出す）

### Round 2：2人目のレビュワー（検証する目）

> 「1人目のメモ＋これまでの試行錯誤を知っている上級エンジニア」として評価

- **既に試したこと・わかっていることと矛盾しないか** 確認
- **エラーメッセージ・症状と一致するか** 確認
- **外部依存を見落としていないか** 確認（設定ファイル・外部サービス・テンプレート）
- 各仮説に可能性★を付けて優先順位を決める

## この手法を生んだ実例：パスワードリセットのデバッグ（2026年5月）

### 症状
パスワードリセットのメールが届いてリンクをクリックしても、毎回「Create account」ページに飛ばされる。

### 試したが効果がなかったこと
| 試したこと | 結果 |
|---|---|
| `callback/route.ts` に `token_hash` 対応追加 | 効果なし |
| `proxy.ts` に `reset-password` を例外追加 | 効果なし |
| `resetPasswordForEmail` をクライアント側に移動（PKCEのため） | 効果なし |

### デュアルレビューで気づいたこと
1人目のレビュワーとして全コードを読み直したとき、**Supabase のメールテンプレート**を初めて確認。

```html
<!-- 問題のテンプレート -->
<a href="https://[supabase].supabase.co/auth/v1/verify
  ?token={{ .Token }}
  &type=recovery
  &redirect_to=https://site/auth/callback?next=/auth/reset-password">
```

**2つの問題が発覚：**
1. `redirect_to` がテンプレートに**直書き**されていた → コードの `redirectTo` が完全に無視されていた
2. `{{ .Token }}` という旧形式 → implicit flow（ハッシュ方式）が確定していた

### 解決策
テンプレートを1行に変更するだけで解決：

```html
<a href="{{ .ConfirmationURL }}">Reset Password</a>
```

`{{ .ConfirmationURL }}` = Supabase が自動生成する変数。コードの `redirectTo` を使い、PKCE に対応。

## 教訓

### 1. メール認証のバグはテンプレートから見る
```
正しい調査順序：
  メールテンプレート → コード → サービス設定

やりがちな間違い：
  コード → コード → コード → （ずっとコードを見る）
```

### 2. 「コードの外」を忘れない
バグの原因はコードだけじゃない。以下も必ず確認対象に含める：
- メールテンプレート
- 外部サービスの設定（Supabase、Stripe、SendGrid など）
- 環境変数・シークレット
- DNS・リダイレクト設定

### 3. エラーコードは正直
`otp_expired` → トークン期限切れ（ただし、テンプレートのせいで毎回起きていた）
`access_denied` → アクセス拒否

エラーコードが示している内容を信じる。「コードが悪いはずだ」という思い込みを捨てる。

### 4. 「試したが直らなかった」事実を最大活用する
同じことを何度試しても直らない場合、**原因の場所が違う**。
スコープを広げて、コードの外を疑う。
